# Наполнение реестра данными

Порядок импорта JSON-снимков в локальную базу. Соответствует разделам
2 («Модель данных»), 6 («Импорт и версионирование снимков») и 7
(«Обработка ошибок») ТЗ.

## 1. Формат входных файлов

Входной файл — JSON-массив объектов. Каждый объект описывает один
стандарт и должен содержать поля (имена полей — точно как в исходной
выгрузке открытых данных, включая завершающий пробел в имени второго
поля):

| Поле | Обязательность | Назначение |
|---|---|---|
| `Обозначение` | обязательно | Обозначение стандарта, например `ГОСТ Р 2.101-2023` |
| `Заглавие на русском языке ` (с пробелом в конце имени поля) | обязательно | Название стандарта |
| `Статус` | опционально | Статус действия (например, «Действует») |
| `Код ОКС` | опционально | Один или несколько кодов ОКС |

Пустое или отсутствующее значение в обязательном поле — причина
отклонения записи (см. раздел 4), а не остановки всего импорта.

## 2. Где размещать файлы

Поместите один или несколько JSON-файлов в каталог `data/incoming/`
проекта (или в подкаталог внутри него, если ведёте несколько выгрузок
раздельно). В поставке уже присутствуют два исходных файла пользователя:

- `data/incoming/ListJSONGostOpenData_11.08.2026-13_33_24.json` — 112 записей серии ГОСТ;
- `data/incoming/ListJSONGostROpenData_11.08.2026-13_30_52.json` — 106 записей серии ГОСТ Р.

Это неполный набор — пользователь предупредил, что полные файлы будут
предоставлены позже. Дальнейшие обновляющие или замещающие выгрузки
следует помещать туда же (или в новый подкаталог, см. раздел 5) без
изменения кода.

## 3. Импорт: dry-run, затем активация

Импорт — двухшаговый процесс намеренно: сначала предпросмотр отчёта
без изменения активного снимка, затем осознанная активация.

Шаг 1 — предпросмотр:

```bash
source .venv/bin/activate
python -m gost_registry.importer \
  --input-dir ./data/incoming \
  --snapshot-date 2026-08-11 \
  --report ./data/reports/dry-run.json
```

Откройте `data/reports/dry-run.json` и проверьте:

- сколько записей прочитано в каждом файле (`total_read`);
- сколько принято (`imported`), отклонено (`rejected`), сколько
  дублей (`duplicates`) и конфликтов (`conflicts`);
- список отклонённых записей с причиной (`import_rejections`) —
  каждая запись содержит исходное обозначение (если оно было) и
  причину отклонения.

Шаг 2 — активация (снимок становится действующим для всех пяти
MCP-инструментов только после этого шага):

```bash
python -m gost_registry.importer \
  --input-dir ./data/incoming \
  --snapshot-date 2026-08-11 \
  --activate \
  --report ./data/reports/import-2026-08-11.json
```

По умолчанию база — `data/gost_registry.sqlite`; путь переопределяется
флагом `--db`.

## 4. Что блокирует, а что не блокирует импорт

Различение зафиксировано как интерпретация раздела 7 ТЗ (там прямого
указания на этот случай нет — раздел 7.2 требует не прерывать импорт
из-за одной дефектной записи, раздел 7.3 называет отсутствие
обязательного поля «блокирующей ошибкой»; ниже — принятое решение):

| Ситуация | Действие |
|---|---|
| Файл не читается или это не валидный JSON, либо корень не массив | Блокирует активацию **всего** снимка (`--activate` не срабатывает) |
| В отдельной записи отсутствует/пусто обязательное поле | Запись отклоняется в `import_rejections`, импорт остальных записей продолжается |
| Два обозначения после нормализации совпадают, но остальные данные (заглавие, статус, ОКС) различаются | Конфликт — блокирует активацию, если не передан `--allow-conflicts` |
| Полностью идентичная запись встречается повторно (тот же хеш) | Считается дублем, не конфликтом, не блокирует |

Пример принудительной активации при осознанно принятых конфликтах:

```bash
python -m gost_registry.importer \
  --input-dir ./data/incoming \
  --snapshot-date 2026-08-11 \
  --activate \
  --allow-conflicts \
  --report ./data/reports/import-2026-08-11-forced.json
```

Используйте `--allow-conflicts` только после того, как отчёт о
конфликтах проверен вручную — флаг не выбирает «правильную» версию
автоматически, он просто снимает блокировку.

## 5. Обновление реестра новым снимком

1. Новые файлы — в отдельный подкаталог, например
   `data/incoming/2026-09-01/`, либо замените файлы в
   `data/incoming/` целиком (когда придут полные файлы взамен текущих
   неполных).
2. Импорт без `--activate`, разбор отчёта (см. раздел 3).
3. Выборочная сверка критичных записей — например, обозначений серии
   ЕСКД/ЕСТД, которые чаще всего проверяются через `verify_reference`.
4. Повторный запуск с `--activate` только после проверки.
5. Предыдущий активный снимок не удаляется — переводится в статус
   `superseded` и остаётся в базе для аудита и для
   `get_registry_provenance`.

## 6. Проверка после наполнения

```bash
python -m pytest -q
python tests/manual_stdio_client_check.py .venv/bin/python ./data/gost_registry.sqlite
```

Второй скрипт вызывает все пять инструментов на реально активном
снимке — это быстрый способ убедиться, что импортированные вами данные
действительно доступны через MCP, а не только записаны в базу.

## 7. Ограничения раздела (проверенные риски)

- На момент сдачи в `data/incoming/` находится неполный набор данных
  (по словам пользователя — «полные файлы положу позже»); показатели
  218 записей / 0 отклонений / 0 конфликтов, зафиксированные при
  тестовом импорте, относятся именно к этому неполному набору и не
  являются гарантией поведения на полном наборе.
- Формат ожидает конкретные имена полей входной схемы (см. раздел 1);
  выгрузки в ином формате (CSV/XML или JSON с другими именами полей)
  импортёром не поддерживаются без изменения кода.
