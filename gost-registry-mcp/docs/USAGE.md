# Использование

Описание пяти MCP-инструментов сервиса, примеры вызовов на реальных
данных и рекомендованный текст промпта для LLM-субагента нормоконтроля.
Соответствует разделам 6 («Контракт MCP-инструментов») и 8
(«Требования к субагенту») ТЗ.

## 1. Общая форма ответа

Каждый ответ содержит:

```json
{
  "registry_snapshot": {
    "snapshot_id": "...",
    "snapshot_date": "2026-08-11",
    "source_scope": "local_registry"
  },
  "verdict": "...",
  "confidence": 0.0,
  "diagnostics": []
}
```

`confidence` — техническая определённость сопоставления, не
юридическая достоверность стандарта:

- `1.00` — точное совпадение нормализованного обозначения и заглавия;
- `0.95` — точное совпадение обозначения, заглавие не передано;
- `0.70–0.94` — один кандидат при некритичном форматном расхождении;
- `<0.70` — неподтверждённый кандидат, требуется ручная проверка.

## 2. Инструмент `normalize_designation`

Назначение: разбор и нормализация обозначения без обращения к
реестру — работает даже без активного снимка.

Вход:

```json
{"designation": "гост р2.101–2023"}
```

Выход:

```json
{
  "verdict": "parsed",
  "input": "гост р2.101–2023",
  "designation_normalized": "ГОСТ Р 2.101-2023",
  "series": "ГОСТ Р",
  "number_part": "2.101",
  "year": 2023,
  "diagnostics": []
}
```

## 3. Инструмент `resolve_standard`

Назначение: точный поиск одной канонической записи по обозначению.

Вход:

```json
{"designation": "ГОСТ Р 2.101-2023"}
```

При успехе — одна каноническая запись (`standard_id`, обозначение,
заглавие, статус, ОКС, сведения о снимке). При отсутствии —
`verdict = "designation_not_found"`, без выдуманных значений.

## 4. Инструмент `verify_reference` (основной инструмент проверки)

Вход:

```json
{
  "designation": "ГОСТ Р 2.101-2023",
  "title_ru": "Единая система конструкторской документации. Стадии разработки",
  "require_active_status": false
}
```

Возможные значения `verdict`:

| Значение | Условие |
|---|---|
| `verified` | Обозначение и переданное заглавие совпадают |
| `verified_designation_only` | Обозначение найдено, заглавие не передано |
| `title_mismatch` | Обозначение найдено, заглавие не совпадает |
| `designation_not_found` | Обозначение не найдено |
| `ambiguous` | Найдено несколько кандидатов или разбор недостаточен |
| `invalid_input` | Пустой или неразбираемый вход |

При `title_mismatch` ответ всегда содержит каноническое заглавие и не
изменяет переданные пользователем данные.

Пример, воспроизведённый на реальном наборе данных пользователя (при
активном снимке из `data/incoming/`): вызов с обозначением
`ГОСТ Р 2.101-2023` без заглавия вернул `verified_designation_only` с
каноническим заглавием «Единая система конструкторской документации.
Стадии разработки»; тот же вызов с заведомо неверным заглавием вернул
`title_mismatch` с тем же каноническим заглавием без изменения входа.

## 5. Инструмент `search_standards`

Вход:

```json
{
  "query": "электронная структура изделия",
  "series": "ГОСТ Р",
  "ics_code_prefix": "01.110",
  "status": "Действует",
  "limit": 10
}
```

Выход: до `limit` кандидатов с типом совпадения (`exact`, `prefix`,
`token`, `fuzzy`), техническим баллом и каноническими реквизитами.
Поиск не возвращает вердикт `verified` — результат всегда список
кандидатов, требующих дальнейшей проверки через `verify_reference` или
`resolve_standard`.

## 6. Инструмент `get_registry_provenance`

Назначение: сведения о происхождении данных и границах применимости.

Ответ содержит дату импорта, список активных файлов-снимков, контрольные
суммы, число импортированных и отклонённых записей и обязательный текст
ограничения:

«Результат основан на локальном импортированном снимке и не
подтверждает юридическую актуальность вне этого снимка».

Вызывайте этот инструмент первым при работе с новым снимком или перед
формированием отчёта, где важно указать источник данных.

## 7. Рекомендованный промпт для LLM-субагента (Qwen Code и аналогичные)

Ниже — точный текст промпта из ТЗ (раздел 8.3). Используйте его как
системный промпт или как инструкцию в начале задачи, если поручаете
Qwen Code (или другому агенту) массовую проверку ссылок на стандарты
через инструменты `gost-registry`.

```text
Ты — субагент нормоконтроля библиографических ссылок на стандарты.

Твоя задача: проверять ссылки на ГОСТ, ГОСТ Р, ПНСТ и адаптированные
международные стандарты только через доступный MCP-сервис «ГОСТ-реестр».

Правила:
1. Не используй собственные знания для подтверждения номера, названия,
   статуса или актуальности стандарта.
2. Сохраняй исходную ссылку пользователя без изменений.
3. Если выделено обозначение, вызови verify_reference с обозначением и
   заглавием, если оно присутствует.
4. Если обозначение отсутствует или неразбираемо, но есть заглавие,
   вызови search_standards. Результаты поиска являются кандидатами, а
   не подтверждением.
5. Не отождествляй «ГОСТ» и «ГОСТ Р», «ГОСТ ISO» и «ГОСТ ИСО», разные
   годы, части или номера.
6. При verified выдай канонические реквизиты и ссылку на снимок
   реестра.
7. При title_mismatch зафиксируй: обозначение найдено, но указанное
   заглавие не соответствует; приведи каноническое заглавие как
   предложение для ручной проверки.
8. При designation_not_found зафиксируй отсутствие в локальном снимке;
   не утверждай, что такого стандарта не существует вообще.
9. При ambiguous выдай список кандидатов и направь вопрос на ручную
   проверку.
10. Не вноси изменения в sources, requirements, documents или граф без
    отдельной подтверждённой команды.

Формат результата для каждой найденной ссылки:
- Исходная ссылка
- Вердикт
- Каноническая запись или кандидаты
- Снимок реестра
- Диагностика
- Рекомендуемое действие

Формулировка ограничения обязательна при любом отрицательном
результате: «Проверка выполнена по локальному импортированному снимку
реестра; результат не подтверждает отсутствие стандарта в иных
источниках и не определяет его юридическую применимость».
```

Правило 1 этого промпта — ключевое ограничение по замыслу ТЗ: субагент
не должен подтверждать существование, название или статус стандарта из
собственных знаний модели, только через вызовы инструментов сервиса.

## 8. Типичный сценарий проверки в Qwen Code

1. Убедитесь, что сервер подключён (`docs/DEPLOYMENT.md`, раздел 5.3).
2. В начале задачи по нормоконтролю передайте агенту промпт из раздела 7
   этого документа.
3. Дайте агенту текст документа или список ссылок на стандарты для
   проверки.
4. Ожидаемое поведение агента: для каждой найденной ссылки — вызов
   `verify_reference` (или `search_standards`, если обозначение не
   выделено), вывод в формате из раздела 7, без утверждений от себя.
5. Для итогового отчёта по всему набору — отдельный вызов
   `get_registry_provenance`, чтобы приложить сведения о снимке и
   дисклеймер.

## 9. Ограничения раздела (проверенные риски)

- Примеры вывода в разделах 2–4 воспроизведены на неполном наборе
  данных (218 записей из двух файлов пользователя); на полном наборе
  возможны новые случаи `ambiguous` (несколько кандидатов), которых в
  текущих тестовых данных не встретилось.
- Поведение конкретно Qwen Code при получении промпта из раздела 7 (в
  части строгого следования правилу «не использовать собственные
  знания») зависит от модели, стоящей за Qwen Code, и не гарантируется
  сервисом — сервис гарантирует только корректность ответов
  инструментов, не поведение вызывающей модели.
