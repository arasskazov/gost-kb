# MCP-сервис «ГОСТ-реестр»

Локальный MCP-сервис для детерминированной библиографической проверки
ссылок на стандарты (ГОСТ, ГОСТ Р, ПНСТ, адаптированные международные
стандарты вида ГОСТ ISO / ГОСТ ИСО) по импортированному снимку открытых
данных. Реализация выполнена по ТЗ «MCP-сервис «ГОСТ-реестр»» (раздел
9), без Docker — для локального развёртывания на Pop!_OS.

Полное описание архитектуры, модели данных, правил нормализации и
контракта инструментов — см. исходное ТЗ. Настоящий README даёт общий
обзор и краткий запуск; подробные инструкции — в каталоге `docs/`:

- [`docs/DEPLOYMENT.md`](docs/DEPLOYMENT.md) — установка, запуск MCP-сервера (stdio/сетевой/systemd), подключение к Qwen Code.
- [`docs/DATA.md`](docs/DATA.md) — формат входных JSON, наполнение и обновление реестра, dry-run/активация, обработка ошибок импорта.
- [`docs/USAGE.md`](docs/USAGE.md) — контракт всех пяти MCP-инструментов с примерами, промпт для LLM-субагента нормоконтроля, типичный сценарий проверки.

## 1. Что делает сервис и чего не делает

Делает:

- импортирует произвольное число JSON-файлов с записями `Обозначение`,
  `Заглавие на русском языке ` (с завершающим пробелом в имени поля —
  это особенность исходной схемы выгрузок), `Статус`, `Код ОКС`;
- хранит их как версионируемые снимки в локальной SQLite;
- отвечает на пять MCP-запросов только для чтения: `normalize_designation`,
  `resolve_standard`, `verify_reference`, `search_standards`,
  `get_registry_provenance`.

Не делает:

- не подтверждает юридическую применимость или актуальность стандарта
  вне даты импортированного снимка;
- не хранит сведения об отмене, замене, поправках, если они не были
  явно импортированы;
- не изменяет исходные документы, требования или граф проекта.

## 2. Требования к системе (Pop!_OS)

- Python 3.10 или новее (в Pop!_OS 22.04 доступен через `python3`;
  в Pop!_OS 24.04 системный Python уже 3.12 — подходит без действий).
- Пакет `python3-venv`, если модуль `venv` не установлен по умолчанию:

  ```bash
  sudo apt update
  sudo apt install -y python3-venv python3-pip
  ```

- Docker не требуется и не используется.

## 3. Установка

```bash
cd ~/gost-registry-mcp     # каталог, куда распакован проект
python3 -m venv .venv
source .venv/bin/activate
pip install --upgrade pip
pip install -e ".[dev]"
```

Зависимость MCP SDK зафиксирована как `mcp>=1.2.0,<2.0.0` в
`pyproject.toml`. Это осознанное ограничение: ветка `mcp` 2.0.0
переименовала используемый здесь класс `FastMCP` в `MCPServer` и
изменила внутренний API. Данный сервер написан под стабильную и широко
документированную линию 1.x. Не снимайте верхнюю границу версии без
пересмотра `src/gost_registry/mcp_server.py`.

## 4. Проверка перед первым импортом (тесты)

```bash
python -m pytest -q
```

Ожидаемый результат — все тесты пройдены (набор покрывает нормализацию,
импорт, конфликты/дубли, репозиторий и доменную логику всех пяти
инструментов). Запускайте тесты после любого изменения кода перед тем,
как переимпортировать реальные данные.

## 5. Импорт JSON-снимка

1. Поместите ваши JSON-файлы (например, выгрузки ГОСТ и ГОСТ Р) в
   каталог `data/incoming/`. В поставляемой архивации там уже лежат ваши
   два исходных файла (`ListJSONGostOpenData_11.08.2026-13_33_24.json`,
   `ListJSONGostROpenData_11.08.2026-13_30_52.json`) — можно сразу выполнить импорт
   без дополнительных действий, либо заменить их более поздними выгрузками.
2. Выполните dry-run без активации, чтобы увидеть отчёт до применения:

   ```bash
   python -m gost_registry.importer \
     --input-dir ./data/incoming \
     --snapshot-date 2026-08-11 \
     --report ./data/reports/dry-run.json
   ```

3. Проверьте отчёт: число прочитанных, импортированных, отклонённых
   записей, дубликаты и конфликты.
4. Если отчёт устраивает — повторите запуск с `--activate`:

   ```bash
   python -m gost_registry.importer \
     --input-dir ./data/incoming \
     --snapshot-date 2026-08-11 \
     --activate \
     --report ./data/reports/import-2026-08-11.json
   ```

По умолчанию база создаётся в `data/gost_registry.sqlite`. Путь можно
переопределить флагом `--db`.

Конфликт одинакового `designation_normalized` с разными реквизитами
блокирует активацию, если не передан `--allow-conflicts`. Это
намеренное поведение (раздел 7.2 ТЗ) — конфликт требует ручного
решения оператора, а не автоматического выбора одной из версий.

## 6. Запуск MCP-сервера (stdio)

```bash
source .venv/bin/activate
python -m gost_registry.mcp_server --transport stdio --db ./data/gost_registry.sqlite
```

Процесс ожидает подключение MCP-клиента по стандартному вводу/выводу и
не завершается сам — это нормально, остановка по Ctrl+C.

### Подключение из MCP-клиента (пример конфигурации)

Для клиентов, поддерживающих формат `mcpServers` (Claude Desktop,
большинство совместимых IDE-плагинов), добавьте запись, указав
абсолютные пути вашей установки:

```json
{
  "mcpServers": {
    "gost-registry": {
      "command": "/home/<user>/gost-registry-mcp/.venv/bin/python",
      "args": [
        "-m",
        "gost_registry.mcp_server",
        "--transport",
        "stdio",
        "--db",
        "/home/<user>/gost-registry-mcp/data/gost_registry.sqlite"
      ]
    }
  }
}
```

Замените `<user>` и пути на реальные для вашей машины Pop!_OS.

### Автозапуск без Docker (опционально, через systemd --user)

Если сервис нужен постоянно запущенным локально без ручного старта
терминала — можно завести пользовательский systemd-юнит (это не
Docker, обычный процесс Linux):

```ini
# ~/.config/systemd/user/gost-registry-mcp.service
[Unit]
Description=MCP gost-registry (stdio)

[Service]
Type=simple
ExecStart=/home/%u/gost-registry-mcp/.venv/bin/python -m gost_registry.mcp_server --transport stdio --db /home/%u/gost-registry-mcp/data/gost_registry.sqlite
Restart=on-failure

[Install]
WantedBy=default.target
```

```bash
systemctl --user daemon-reload
systemctl --user enable --now gost-registry-mcp.service
```

Транспорт `stdio` рассчитан на запуск по требованию клиентом, а не на
постоянный демон — использование systemd-юнита оправдано только если
ваш MCP-клиент ожидает уже запущенный процесс, к которому подключается
иначе (например, через сетевой транспорт, см. ниже). Для обычного
локального использования (Claude Desktop и подобные) достаточно
конфигурации из предыдущего раздела — клиент сам запускает и завершает
процесс.

### Сетевой транспорт (опционально, без Docker)

Если нужен доступ нескольким процессам/агентам одновременно:

```bash
python -m gost_registry.mcp_server \
  --transport streamable-http \
  --host 127.0.0.1 \
  --port 8080 \
  --db ./data/gost_registry.sqlite
```

Публикуйте порт только на `127.0.0.1` либо за отдельным reverse proxy
с TLS и аутентификацией, который вы настраиваете самостоятельно (nginx,
Caddy и т. п. — без Docker, обычной установкой из `apt`). Сервис сам
никакой аутентификации не предоставляет.

## 7. Ручная проверка живого протокола (опционально)

`tests/manual_stdio_client_check.py` — разовый скрипт, поднимающий
настоящего MCP stdio-клиента и вызывающий все пять инструментов на
активном снимке. Не входит в автоматический набор pytest, использовался
при приёмке. Запуск:

```bash
python tests/manual_stdio_client_check.py .venv/bin/python ./data/gost_registry.sqlite
```

## 8. Обновление реестра новым снимком

1. Новые JSON — в отдельный подкаталог, например
   `data/incoming/2026-09-01/`.
2. Импорт без `--activate`, разбор отчёта.
3. Выборочная сверка критичных записей (например, ЕСКД/ЕСТД).
4. Повторный запуск с `--activate` только после ручной проверки.
5. Предыдущий активный снимок не удаляется — переводится в статус
   `superseded` и остаётся в базе для аудита.

## 9. Структура проекта

```text
gost-registry-mcp/
  src/gost_registry/
    config.py         — пути и константы по умолчанию
    models.py          — Pydantic-модели входа/выхода
    normalization.py    — чистые функции нормализации (без БД)
    importer.py          — CLI импорта JSON-снимков
    repository.py         — схема SQLite и SQL-операции
    service.py             — доменная логика пяти MCP-операций
    mcp_server.py            — MCP-сервер (FastMCP, stdio по умолчанию)
  tests/                       — pytest: нормализация, импорт, репозиторий, сервис
  data/incoming/                — входные JSON (не публикуются в git)
  data/reports/                   — отчёты импорта (не публикуются в git)
```

## 10. Известные ограничения реализации (проверенные риски)

- MCP SDK `mcp` в очень свежих версиях (2.0.0+) меняет высокоуровневый
  API (`FastMCP` → `MCPServer`); зависимость закреплена ниже этой
  границы. Обновление требует ревизии `mcp_server.py`.
- Реестр отвечает только по активному снимку; при его отсутствии все
  вызовы верификации возвращают `designation_not_found` с явной
  диагностикой отсутствия активного снимка — это не означает
  отсутствие стандарта в реальности.
- Раздел 4.1 ТЗ описан для одно-файлового снимка; здесь снимок может
  объединять несколько файлов, файловый уровень вынесен в отдельную
  таблицу `snapshot_files` без потери требуемых ТЗ полей (см.
  комментарий в начале `repository.py`).
- Раздел 7.3 ТЗ смешивает блокирующие ошибки файла и записи; здесь они
  разделены явно (см. комментарий в начале `importer.py`): дефектная
  запись отклоняется без остановки импорта, но нечитаемый/невалидный
  JSON-файл блокирует активацию всего снимка.
